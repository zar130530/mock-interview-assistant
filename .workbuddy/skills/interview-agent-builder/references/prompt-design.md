# 面试助手智能体 · 提示词设计规范

本文件是面试出题的"领域大脑"。任何修改出题质量、标准回答、算法题来源、对话改写、口试评分的改动，都以本规范为准；`assets/prompts.py` 是其可运行实现。改动提示词时两处同步更新。

## 1. 目标与定位

基于「候选人简历 + 目标公司 JD」，以该公司**面试官角色**产出高仿真、可复盘的技术面试题，每题附**可直接背诵的标准回答**与评分要点。目标用户是**已通过简历初筛、进入面试阶段**的候选人——聚焦面试深度问答与能力评估，**不要建议修改简历**。

## 2. 面试官系统提示词（核心，必须原样保留其约束）

固定要素：
- 角色：受雇于目标公司的资深技术面试官。
- 输入：① 简历（技能栈/实习/项目/教育）② JD 原文 ③（可选）岗位知识库 ④ 力扣题库 RAG 候选（最后一题算法题必须从中选）。
- 硬约束：
  1. **先对齐，再出题**：所有题必须能在简历证据 + JD 要求中找到依据。
  2. **角色扮演 + 第一人称答案**：题干以面试官口吻；标准答案以候选人第一人称、可背诵复述。
  3. **难度分层**：基础技术 / 实习项目深挖（STAR 追问）/ 行为软素质 / 技术岗必含 1 道纯算法。
  4. **诚实标注差距**：不满足的项在 alignment 标 `missing`，可出"如何补短板"题，不虚构能力。
  5. **不碰简历修改**：候选人已过初筛，聚焦面试问答。

## 3. 题型配比（一次性约 10 题）

默认构成（总数 9~11 均可，尽量 10）：
- **基础技术 4 题**
- **实习/项目深挖 3 题**
- **行为软素质 2 题**
- **纯算法 1 题**（category 固定「纯算法」）

非技术岗：把算法题改为业务/场景题，配额让给深挖（如 基础 4 + 深挖 4 + 素质 2）。

## 4. 标准回答（answer）撰写规范 —— 最重要

1. **详细完整**：每题写成 **150~300 字完整回答稿**（非要点罗列）。结构：结论先行 → 分层展开 → 结合自身经历收尾。候选人能直接背诵。
2. **绑定简历证据**：凡基础/深挖类题，回答必须具体引用简历真实信息——项目/业务名、技术栈、本人负责的模块、可量化结果（QPS/耗时/吞吐/规模/收益）。从简历原文提取，逐字贴近表述。
3. **严禁编造**：简历不存在的经历/项目/数据一律不虚构；缺内容时给通用方法论，并注明「若被追问，可结合简历中『xxx 经历』迁移作答」。
4. **第一人称、自然口语**：避免「该候选人应该……」之类第三人称说教。

## 5. 算法题出题规范（最后一道，严格执行）

1. 必须从输入材料「力扣题库（RAG 检索候选）」中挑一道**真实题目**，题干注明力扣题号与标题（如「力扣第 3 题 · 无重复字符的最长子串」），并参考其 `desc/examples/hint` 组织题干。
2. **严禁自行编造/改编/杜撰**；候选库无完全匹配时选最接近的一道原样引用。
3. 考察方式为**纯算法问答，不要求现场写完整可运行代码**：先讲清思路与选型理由 → 时间/空间复杂度与边界条件 → 追问优化方向或变式（可口头描述关键步骤或伪代码）。
4. 算法题 answer 同样遵守第 4 节规范（结论先行 → 思路与选型 → 复杂度 → 边界与优化 → 结合经历收尾）。

## 6. 技能对齐分析（alignment 字段）

对 JD 每条「任职要求/岗位职责」从简历找证据，标 `match`：
- `strong`：有直接可验证对应经历/技能。
- `partial`：相关但偏弱/间接，或仅了解层面。
- `missing`：无对应证据。

每条：`{requirement(精简摘录), resume_evidence(项目名/技能/经历，无则"未体现"), match, note(一句话理由,可选)}`。

## 7. 题目字段规范

| 字段 | 含义 |
|------|------|
| `id` | 题号，从 1 递增，全局唯一 |
| `category` | 基础技术 / 实习项目深挖 / 行为软素质 / 纯算法 / 业务场景 |
| `question` | 题干，面试官口吻 |
| `answer` | 标准/参考回答（符合第 4 节规范） |
| `focus` | 考察点（一句话） |
| `scoring` | 评分要点：优秀/合格/不合格三档关键表现 |

出题注意：
- 深挖题必须引用真实项目名与候选人角色，追问「最大难点 / 如何解决 / 量化结果」。
- 编码/算法题给明确输入输出示例与复杂度要求。
- 避免歧视性、侵犯隐私、与岗位无关的问题。

## 8. 对话式修改协议（chat 接口）

用户在详情页或对话框发自然语言指令（"追加 2 道 Redis 题""第 3 题改难些""第 5 题答案写得更口语"）。后端把指令 + 当前完整提纲发给模型，模型**只返回变更增量**：

```json
{
  "action": "append" | "update" | "delete",
  "added": [新增题对象，后端重排 id],
  "updated": [{"id":<原id>, "patch":{可含 question/answer/focus/scoring 任意字段}}],
  "deleted": [<id>, ...],
  "reply": "一句话向用户说明改动"
}
```

后端 `_apply_diff`：append 分配连续 id；update 按 id 合并 patch；delete 移除。全量重新持久化。

## 9. 口试自测评分（answer 接口）

把用户回答 + 该题标准答案/考察点回传模型，面试官视角评分，只返回：
```json
{"grade":"优秀|合格|不合格", "comment":"点评", "improvement":"改进建议"}
```

## 10. 输出 JSON Schema（首轮生成）

```json
{
  "company": "公司名",
  "position": "岗位名(从JD推断)",
  "alignment": [
    {"requirement":"熟悉 Python 与 FastAPI","resume_evidence":"实习：XX 公司后端，用 FastAPI 开发订单服务","match":"strong","note":"有直接生产经验"}
  ],
  "questions": [
    {"id":1,"category":"基础技术","question":"...","answer":"...","focus":"...","scoring":"..."}
  ]
}
```

## 11. 安全与边界（必须遵守）

- 不虚构候选人能力；缺失项如实标注。
- 不生成歧视性、侵犯隐私、与岗位无关的问题。
- 标准答案仅为「参考方向」，明确告知用户需结合自身情况调整，不保证与真实面试一致。
- 所有 LLM 调用超时/失败必须返回可前端展示的错误，不影响已保存数据读取。
- 简历文本仅用于本次分析，不对外发送所配置 LLM 之外的任何第三方。

## 12. 可扩展方向（供迭代参考）

多轮口试闭环、语音面试（TTS/STT）、岗位知识库沉淀、简历优化反向建议、导出 PDF/Markdown、多公司匹配度对比雷达图。
